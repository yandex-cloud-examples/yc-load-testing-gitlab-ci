## 0. Getting started

Learn about [Yandex Load Testing](https://yandex.cloud/en/docs/load-testing/) in YC documentation.

---

### Select the agents to generate the load

In Yandex Load Testing, the load is generated by nodes known as load testing agents. Currently, Load Testing offers two options for creating these testing agents:
* Agent in Yandex Compute Cloud (for details, see [this step-by-step guide](https://yandex.cloud/docs/load-testing/operations/create-agent)).
* External agent (for details, see [this tutorial](https://yandex.cloud/docs/load-testing/tutorials/loadtesting-external-agent)).

Note that it is the user’s responsibility to manage external load testing agents.

---

### Prepare configuration files for load testing

To prepare configuration and test data files, you need to write and then debug them. We recommend using the management console UI for these tasks.

To learn how to get started with Load Testing and create your first tests, see **Tutorials** in the [Yandex Load Testing documentation](https://yandex.cloud/docs/load-testing/).

## Set up access from GitLab CI to Yandex Cloud

1. [Create](https://yandex.cloud/docs/iam/quickstart-sa) a service account to use for running load tests.
1. Assign the required roles to this service account:
    - `loadtesting.loadTester`
1. Optionally, if you plan to deploy a `compute` load testing agent within your CI pipeline, make sure to also assign the following roles:
    - `iam.serviceAccounts.user`
    - `compute.editor`
    - `vpc.user`
    - `vpc.publicAdmin` (optionally, if you are deploying the agent in a public network).
1. Optionally, to use the repository files as your test data, use an Object Storage bucket as an intermediate storage (CI uploads the data, the agent downloads it, and then CI deletes it):
    - Create a bucket in Object Storage.
    - Grant write permissions using one of the following methods:
        - `storage.editor` (global role in the folder).
        - `editor` (ACL in the bucket).
1. [Create](https://yandex.cloud/docs/iam/concepts/authorization/key) an authorized key for the service account and save the `json` key file to your local disk.
1. [Add](https://docs.gitlab.com/ee/ci/variables/#for-a-project) the `YC_LOADTESTING_CI_AUTHORIZED_KEY_JSON` variable to **GitLab CI** settings. Paste the contents of the downloaded `json` file with the authorized key as the variable value.

## Add the load testing configuration files to the repository

Create a separate folder for every test you are going to run:
  - Save the configuration file in `test-config*.yaml` format.
  - Place the test data files to the same location. They will be temporarily uploaded to Object Storage before the test, and then the agent will download them when the test runs.

In this scenario, the test name matches the name of the folder containing the configuration file. 

_**Note: You can learn more about how to override the name of the test being created and other run settings [here](README-howto-add-test.md).**_

_**For examples, see the [`sample-tests`](sample-tests/) folder.**_

## Set up a GitLab CI pipeline to run load tests

### Add automation scripts to the repository

Copy scripts from the [`automation`](automation/) folder to your repository. 

For clarity, we assume that this folder is located at the root level. When renaming it or copying to a different location, change the script call paths accordingly: `automation/test.sh blahblah` → `my/custom/dir/test.sh blahblah`. 

### Create a parent `job` with the required test environment configuration

To create tests and manage agents within your CI pipeline, do the following:
  - Install the `curl` and `jq` command-line utilities.
  - Install and configure [YC CLI](https://yandex.cloud/docs/cli/).

In this use case, we will create a template named `.test-loadtesting-template` and inherit all our future CI steps from it using `extends: .test-loadtesting-template`.

```yaml
# .gitlab-ci.yml

.test-loadtesting-template:
  variables:
    # Service account authorized key
    YC_LT_AUTHORIZED_KEY_JSON: ${YC_LOADTESTING_CI_AUTHORIZED_KEY_JSON} 
    # Yandex Load Testing folder ID
    YC_LT_FOLDER_ID: '%%%_CHANGE_ME_%%%'
  before_script: 
    - if [[ -z $YC_LT_AUTHORIZED_KEY_JSON ]]; then exit 1; fi
    - if [[ -z $YC_LT_FOLDER_ID ]]; then exit 1; fi

    # ----------------------------- install utilities ---------------------------- #
    - DEBIAN_FRONTEND=noninteractive apt update
    - DEBIAN_FRONTEND=noninteractive apt install -y curl jq

    - curl -f -s -LO https://storage.yandexcloud.net/yandexcloud-yc/install.sh
    - bash install.sh -i /usr/local/yandex-cloud -n
    - ln -sf /usr/local/yandex-cloud/bin/yc /usr/local/bin/yc

    # ----------------------------- configure yc cli ----------------------------- #
    - echo "${YC_LT_AUTHORIZED_KEY_JSON}" > key.json
    - yc config profile create sa-profile
    - yc config set service-account-key key.json
    - yc config set format json
    - yc config set folder-id ${YC_LT_FOLDER_ID}
```

_**Note: To avoid setting up the environment on every run, you might want to configure it directly in GitLab Runner.**_

### Optionally, add steps to manage temporary `compute` agents

To prevent agent VMs from running continuously, include steps for creating and deleting them within the `pipeline`.

```yaml
# .gitlab-ci.yml

stages:
  # Pre-load test stages
  - test-loadtesting
  - test-loadtesting-cleanup
  # Post-load test stages

test-loadtesting-create-agents:
  extends: .test-loadtesting-template-job
  stage: test-loadtesting
  script:
    - set -e
    - automation/agent.sh create --count 2 \
        --description "CI agent" \
        --labels "pipeline=${CI_PIPELINE_IID}" \
        --service-account-id "###SECRET###" \
        --zone "###SECRET###" \
        --network-interface "subnet-id=###SECRET###,security-group-ids=###SECRET###" \
        --cores 2 \
        --memory 2G

test-loadtesting-delete-agents:
  extends: .test-loadtesting-template-job
  stage: test-loadtesting-cleanup
  when: always
  interruptible: false
  script:
    - set -e
    - automation/agent.sh delete \
        --labels "pipeline=${CI_PIPELINE_IID}"
```

  1. `test-loadtesting-create-agents`: Creates agents. Replace the parameters provided in `automation/agent.sh create` with your own values.
      - `stage: test-loadtesting`: Stage to run your tests at.
      - `automation/agent.sh create`: Compatible with`yc loadtesting agent create` but features `--count` for creating multiple agents simultaneously.

  1. `test-loadtesting-delete-agents`: Deletes agents.
      - `stage: test-loadtesting-cleanup`: Stage to run regardless of whether the steps for creating agents or running tests fail.
      - `automation/agent.sh delete`: Auxiliary script that deletes agents with labels specified in `--labels "label1=valu1,label2=value2"`.

### Define the step for running load tests

```yaml
# .gitlab-ci.yml

stages:
  # Pre-load test stages
  - test-loadtesting
  # Post-load test stages

test-loadtesting-run:
  extends: .test-loadtesting-template-job
  stage: test-loadtesting

  # Resource group that prevents concurrently running 
  # load tests from multiple pipelines.
  resource_group: loadtesting 

  # Step to create `compute` agents.
  needs: [test-loadtesting-create-agents] 

  script:
    - set -e

    # `automation/test.sh` can replace ${YC_LT_TARGET}
    # in test configuration files.
    #
    - export YC_LT_TARGET="###SECRET###"
  
    # Name of the Object Storage bucket used to deliver
    # test data files from the repository to the agent.
    #
    - export YC_LT_DATA_BUCKET="###SECRET###"

    # Defining a criterion for selecting agents to run tests on.
    #
    - export YC_LT_TEST_AGENT_FILTER="labels.pipeline = '${CI_PIPELINE_IID}'"

    # Adding a pipeline link to the description of the tests being created.
    #
    - export YC_LT_TEST_EXTRA_DESCRIPTION="GitLab CI url - ${CI_PIPELINE_URL}"

    # Providing a list of tests to run.
    #
    - automation/test.sh \
        sample-tests/smoke \
        sample-tests/mixed-synthetic-payload \
        sample-tests/mixed-irl-payload \
        sample-tests/mixed-irl-payload-multi \
        sample-tests/root-const \
        sample-tests/root-imbalance

```

`automation/test.sh` accepts directories that contain test configurations. For each test directory, the script follows these steps:
* Preparing:
  1. Labels all non-configuration files within a directory as test data files.
  1. Uploads test data files to the `YC_LT_DATA_BUCKET` bucket.
  1. Retrieves the parameters for test creation from `meta.json`. These parameters include test description, test labels, required agent labels, additional test data files, and the number of agents to run concurrently.
* Running:
  1. Creates a test.
  1. Waits for the test to complete.
* Checking with `automation/_test_check.sh`:
  1. Runs the `test_dir/check_summary.sh` script to check test results.
  1. Runs the `test_dir/check_report.sh` script to check test results.

Additionally, `automation/test.sh` considers the following environment variables:
* `YC_LT_DATA_BUCKET`: Name of the Object Storage bucket used to transfer test data files stored in the repository to the agent.
    - **WARNING: Make sure the service account used to run the agent have permissions to read files in this bucket.**
    - **WARNING2: Make sure the service account whose key is used in GitLab CI has permissions to upload files to this bucket.**
* `YC_LT_TEST_AGENT_FILTER`: Additional filter for selecting agents.
    - _**Note: You can use the CLI to validate the filter:**_  
      `yc loadtesting agent list --filter "MY_FILTER_STRING"`.
* `YC_LT_SKIP_TEST_CHECK`: Flag to skip the check stage. Set any value other than `0` to disable it.
